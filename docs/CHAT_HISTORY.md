## How it works
Normalize the query → pull candidates with a capped `LIKE` query → re-rank in PHP → drop scores below 0.40.

- **Normalizing:** it lowercases, strips diacritics and apostrophes, and turns other punctuation into spaces.
- **Candidates:** the whole phrase, each word as a prefix, and up to 12 inner 3-letter pieces, which is what catches typos. They are ordered by how many patterns they hit, so the cap of 200 keeps the best ones, not arbitrary ones.
- **Re-ranking:** per-word Levenshtein (so word order doesn't matter), partial-word credit, trigram similarity and prefix bonuses. A penalty keeps "wither 3" from matching every title that merely ends in "3". The full formula is in `docs/SEARCH.md`.

I tuned the weights after looking at real scores. A lone matching digit scored 0.45, which is why the penalty exists.

## Complexity and scale limit
- **SQL pass:** O(products × patterns). `LIKE '%x%'` can't use an index, so this is a full scan.
- **PHP re-rank:** bounded by the 200-candidate cap, so it doesn't grow with the catalog.

I measured this on generated catalogs (MariaDB sandbox, untuned):

| Products | SQL pass | PHP re-rank |
|---|---|---|
| 120 (the seed) | 0.6 ms | under 0.1 ms |
| 10,000 | 16 ms | about 1 ms |
| 50,000 | 76 ms | about 1 ms |
| 100,000 | 144 ms | about 1 ms |

A two-typo query costs about 1.5× the SQL time. My limit: comfortable to about 10–20k products, acceptable to about 50k, not beyond, because every autocomplete keystroke is a full scan.

For production I'd use Meilisearch or Typesense (typo tolerance, prefix search and facets built in), with MySQL staying the source of truth. At larger scale, OpenSearch.

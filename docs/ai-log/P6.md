# P6: Product catalog API (list, detail, filters)

## Prompt

CONTEXT: Products, offers, platforms, regions exist with seed data.
TASK: Implement GET /api/products (filters: platform[], region[], price_min, price_max, genre; sort: price_asc, price_desc, popular, newest, discount; pagination; returns "from price" and offer count) and GET /api/products/{slug} (details + all offers with seller, region, price, stock) plus GET /api/filters (available options with counts).
CONSTRAINTS: Repository layer with prepared statements only, no N+1 queries, response shapes exactly as in ARCHITECTURE.md.
DONE WHEN: Tests cover each filter, each sort, pagination edges, and a 404 for an unknown slug. Show me the EXPLAIN for the main list query.

## Response summary

- **Implemented**: `GET /api/products`, `GET /api/products/{slug}`, `GET /api/filters`. New: `ProductRepository` (prepared statements only; sort text from an enum, never from input), `CatalogService` (maps rows to the documented shapes), `CatalogController`, `ProductFilters` (validation, 422 with per-field details), `ProductSort` enum, migration `004` (genre index). Validator hardened against array-valued params.
- **Statements per request are fixed, no N+1**: list = 2 (rows + count), product page = 2, filters = 4; asserted by a test that counts prepared statements for 1 row vs 5 rows.
- **Semantics decided (documented in ARCHITECTURE.md)**: only buyable offers (active + at least one available key) count; `fromPriceCents` = cheapest buyable offer; `offerCount` = number of buyable offers; `discountPct` = the deal on that cheapest offer only (so price and discount agree); sold-out/inactive products are not listed but their page returns `offers: []`. `price_min`/`price_max` are cents and apply to the from price. Facets are counted with all filters except their own; zero-count options dropped unless selected.
- **Deviations from ARCHITECTURE.md (the doc was updated to match, please review)**: query param names `price_min/price_max/genre` per your prompt (doc said `minPrice/maxPrice`, no genre); `platform`/`region` are `{slug,name}` objects (a bare name cannot be used as a filter value); facet options have `label` besides `value,count`; `genres` facet added; `publisher` added to the product page; **region is on the product, not repeated per offer** (a product is a platform+region listing), so the offers do not carry a `region` field although your prompt listed it.
- **EXPLAIN** (docs/QUERY_PLANS.md): the first version used `EXISTS` for the stock check; EXPLAIN showed a materialized semi-join scanning every available key (7,138 est. rows) and `list()` took 28.8 ms. Rewritten as a scalar `LIMIT 1` subquery: a dependent subquery on the covering index `idx_keys_offer_status`, **4.4 ms (6.5x faster)**, same results.
- **Seeder**: deals now sit on each product's cheapest offer (a discounted offer is the cheapest by definition; otherwise `discountPct` would almost never appear on cards), RNG stream unchanged, stale deals are deleted on re-run. Still 34 deals.
- **Tests**: 74 pass (was 24). `CatalogTest` uses a hand-built fixture (7 products, 13 offers) so every expectation is checkable: each filter and combinations (30 data-set cases), each sort including tie-breaks, pagination walk/edges (past the end, pageSize = total, larger than total), 12 invalid-input cases (422), SQL-injection-ish input, facets (other-filters-only counting, selected zero-count options, empty price), detail shape/offers/stock/sold-out page, unknown slug 404 in the error format. Mutation check: removing the stock filter, flipping price_desc, and an off-by-one OFFSET were each caught (23, 1 and 23 failing tests); sources restored afterwards.
- **Bugs found on the way (mine)**: `DbTestCase` did not load `.env`, so a single test class silently skipped for lack of a DB password (only passed in the full run because ApiTest loaded `.env` first); three wrong test expectations of mine (empty facet is dropped by design, JSON encodes 4.0 as 4, off-by-one in a statement-count assertion); a ternary-precedence PHP fatal in my Validator patch. All fixed; the code behaviour was right in each test case.
- **Not verified**: MySQL 8 (everything ran on MariaDB 10.11, so the EXPLAIN layout and join order may differ on MySQL 8); `docker compose up` (no daemon in the sandbox). Frontend not touched.
- **Open questions**: should sold-out products be listed (with "out of stock") instead of hidden? Should `q`/relevance be added to this endpoint when the search task comes?

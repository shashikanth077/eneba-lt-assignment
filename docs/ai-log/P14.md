# P14: Sign-up/sign-in forms, cart, checkout (Stripe), orders with keys, emails

## Prompt

TASK: Build /login and /register (validated forms, server error display), /cart (quantity edit, remove, totals), /checkout (order summary, Stripe Payment Element in test mode, success/failure states, redirect to the order page), and /account/orders (list + detail with a "reveal key" and copy-to-clipboard button). After a successful order, send a confirmation email via EmailJS containing the order number and items but NOT the keys; also send a welcome email on registration.
CONSTRAINTS: Never trust client totals. Keys render only on the order page. Handle the payment pending state while the webhook is still arriving (poll the order status).
DONE WHEN: I can register, buy with Stripe test card 4242 4242 4242 4242, and see my key.

## Response summary

### What was built
- **Forms:** client-side validation (`validation.ts`) shown after blur/submit and blocking the request; server errors still displayed (field errors under fields, alerts for the rest, throttling in minutes).
- **Cart:** quantity stepper (1 to min(5, stock)), remove, line totals and the server's total; every change is a PATCH/DELETE answered with the recomputed cart; flagged lines block checkout.
- **Checkout:** summary from the server cart; visiting reserves nothing; "Continue to payment" calls `POST /api/checkout` with no body (server computes order and amount), then Stripe's Payment Element (dark theme from tokens) with `confirmPayment(redirect: 'if_required')`; the Pay button shows the server's amount. Declined card -> Stripe's message, form stays. Success -> order page. 409 out_of_stock is explained per item; 503/502 messages; only `pk_test_` keys accepted.
- **Order page** `/account/orders/:id`: polls every 2 s while `pending` ("waiting for confirmation"), flips to paid by itself, gives up after 2 min with "Check again"; separate messages for failed/expired/canceled/refund states; other users' orders are "not found". Keys are hidden until "Reveal key" per key, with Hide and Copy (Clipboard API with a visible fallback). `keepUnusedDataFor: 0` removes the keys from the browser's cache when the page closes. The order list links each order and is paginated.
- **EmailJS (browser, public key, as decided in ARCHITECTURE.md):** welcome email after registration; receipt when an order this browser paid for turns paid (localStorage flag set on Pay, consumed once). Params are copied field by field and a test asserts no key appears in anything sent. Not configured or failing -> silently skipped.
- Config: `VITE_STRIPE_PUBLISHABLE_KEY`, `VITE_EMAILJS_*` in frontend/.env.example, docker-compose and README; deps `@stripe/stripe-js`, `@stripe/react-stripe-js`, `@emailjs/browser`.
- Dev helper `backend/tests/bin/dev_order.php` (creates a pending order with the fake payment gateway; used only by the e2e script).

### Verification, and what could NOT be verified
- Frontend: lint, typecheck, build clean; 291 tests (61 new: validation, forms incl. welcome email, cart page, checkout with Stripe stand-ins, order page with fake timers for polling/give-up/expiry, key reveal/copy/clipboard failure, keys not in URL/storage/cache after close, receipt email content and once-only flag, order list).
- Mutation checks (each verified to apply, each failed a test): keys added to the email, keys visible by default, polling off, give-up off, receipt flag ignored, welcome email removed, keys cached after leaving, amount sent in the checkout request (the last two survived at first: tests added), receipt flag not set on Pay, live Stripe key accepted.
- Real browser, real API and database (`e2e/commerce.e2e.cjs`, 27 checks): sign-up with validation, two offers -> cart editing with totals compared to the server's, checkout summary, a pending order, then a correctly **signed webhook** posted to the real endpoint: the order page flips to paid by itself, keys hidden then revealed (format checked), copied to the clipboard (read back), hidden again; the cart badge clears; the list shows Paid and no keys; the key is not in storage, the URL or `GET /api/orders`; another account sees "not found". Earlier scripts still pass (shell 36, home 20, store 22, product 21).
- **Not verified here: the actual card payment.** The sandbox cannot reach js.stripe.com or api.stripe.com and has no Stripe account, so Stripe.js, the Payment Element and a real 4242 payment were not run; the checkout tests use stand-ins for `@stripe/*`, and the e2e plays Stripe's part (fake gateway + signed webhook). Likewise **no real EmailJS email was sent** (no account/templates; the tests mock the SDK). So "DONE WHEN" is verified up to the card form and from the webhook onward, not across the Stripe boundary: on your machine, with your keys and `stripe listen`, that is the one thing left to try.

### Mistakes and fixes along the way
- Real bug caught by the old shell e2e script: validation-on-blur made the helper message appear under the email field and pushed the "Create an account" link down between mouse-down and mouse-up, so the click was lost. A blank helper line is now reserved under the fields.
- One existing test sent a deliberately invalid email to reach the server's 422; client validation now (correctly) stops that, so the test uses a valid-looking value.
- Two mutation survivors (amount in the checkout request, keys staying in the cache) exposed weak tests; strengthened.
- Test helpers: first cart tests queried the list before it loaded; fixed by waiting.

### Decisions and open points
- Receipt email is sent from the browser (as decided earlier): not guaranteed if the tab is closed before the order turns paid, and a technical user could trigger extra receipts to their own address. A server-side email (EmailJS REST with a private key, or SMTP) from the webhook handler would be more reliable.
- After a redirect-based payment method the receipt flag (set before the redirect) still works; only card flows were considered in testing.
- Checkout keeps its payment form in component state; leaving the page abandons that PaymentIntent, and the next checkout replaces the pending order (server behaviour) so keys are not hoarded.

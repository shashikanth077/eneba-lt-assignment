# P31: Railway private networking and network-independent database access

## Prompt

Task: Fix Network-Dependent Railway MySQL Connectivity
Investigate and resolve the issue where the Railway MySQL database connects successfully using mobile data but fails when using certain Wi-Fi networks.
Existing Architecture

* React frontend deployed on Vercel.
* PHP backend deployed on Railway using Dockerfile.
* MySQL database hosted on Railway.
* Local development uses Windows/XAMPP.
* Railway MySQL public TCP proxy is enabled.

Requirements

1. Inspect the existing PHP database connection implementation and identify whether production uses Railway's public TCP proxy or private networking.
2. Configure the Railway PHP backend to connect to Railway MySQL through private networking using the correct internal hostname, port, and existing Railway environment variables.
3. Ensure the React frontend communicates exclusively with the public HTTPS PHP API. Never expose database credentials or connect to MySQL directly from the browser.
4. Ensure local development continues to work with XAMPP's local MySQL configuration independently of Railway production configuration.
5. Separate local and production database configurations without hardcoding credentials or duplicating configuration logic.
6. Verify that the production backend does not depend on the visitor's mobile data, Wi-Fi, ISP, DNS configuration, or access to Railway's public MySQL TCP proxy.
7. Inspect connection timeout handling, error handling, connection reuse, and database health checks.
8. Verify that all existing API functionality continues to work:
   * Homepage sections
   * Product listings and filters

   * Product details

## Response summary

Root cause (inferred, not confirmed on the user's network): the browser never connects to MySQL; only server code does. The Railway public TCP proxy is a non-standard-port host that some Wi-Fi networks block, which breaks whatever runs on that network (Workbench, `mysql`, `php bin/seed.php` or XAMPP pointed at Railway), while mobile data passes. A backend inside Railway is not affected by a visitor's network at all; the remaining risk is a backend still configured with the public proxy host (the earlier docs recommended it for a Vercel-hosted backend), or leftover `DB_*` variables overriding the URL.

Changes: `config/settings.php` now reads Railway's `MYSQL_URL` (new `App\Support\DatabaseUrl`: percent-decodes credentials, rejects non-mysql URLs; individual `DB_*`/`MYSQL_*` variables still win, so XAMPP's `.env` is untouched); a fixed 5-second PDO connect timeout so an unreachable database answers `503 db_unavailable` quickly; docs/RAILWAY.md section "Private networking" (variable, deleting leftover `DB_*`, retry at boot, verification, what each failure means); `.env.example`; 3 new PHPUnit tests. Inspected, unchanged: one lazily created non-persistent PDO per request, error mapping to 503 with the reason only in the log, `/api/health` with `SELECT 1`.

Verified locally: configured only by `MYSQL_URL` (escaped password) the API serves health, products, homepage, filters, upcoming, categories and demo sign-in; unreachable host gives immediate 503; PHPUnit 386 (cart, checkout, orders, keys, auth, profile included). NOT verified: anything on Railway. `mysql.railway.internal` resolution from the deployed backend, "private networking is working", and tests from different networks need the user's project; docs/RAILWAY.md lists the exact checks. The issue is therefore not claimed fixed.

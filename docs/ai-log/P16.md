## 3. Redux Toolkit + Redux Saga Architecture

Implement a central Redux store using Redux Toolkit.

Responsibilities:

**Slice**
- Store feature-specific state.
- Define synchronous reducers.
- Define request, success and failure actions.
- Track loading and error states.
- Avoid putting API logic inside reducers.

**Saga**
- Listen for asynchronous request actions using `takeLatest`, `takeEvery` or other appropriate Saga effects.
- Call service methods.
- Dispatch success or failure actions.
- Handle cancellation, retries and error scenarios where appropriate.

**Service**
- Handle HTTP requests using the shared Axios client.
- Keep endpoint-specific API logic separate from Redux and UI components.

**Selectors**
- Provide reusable selectors for accessing feature state.
- Avoid duplicating state calculations in components.

### Example Redux Saga flow

```text
React Component
      |
      | dispatch(fetchProductsRequest())
      v
Redux Slice
      |
      | request action
      v
Redux Saga
      |
      | calls productService.getProducts()
      v
Axios API Client
      |
      v
PHP Backend API
      |
      | API response
      v
Redux Saga
      |
      | dispatch success / failure
      v
Redux Slice
      |
      | updates state
      v
React Component
      |
      | useSelector()
      v
Updated UI
```

## Response summary

### Decision
The existing app (P8-P15) used RTK Query and MUI. This prompt specifies a different stack, so I treated it as a rebuild of the frontend on the new stack, keeping everything that was independent of it: the API contract types, the pure logic (URL query model, offer sorting, did-you-mean, redirect safety, home-block validation, EmailJS/receipt logic) and, above all, the accessible names and roles, so the existing tests and browser scripts could be ported instead of rewritten. Dependencies removed: `@mui/*`, `@emotion/*`; added: `axios`, `redux-saga`, `react-hook-form`, `zod`, `@hookform/resolvers`, `lucide-react`, `sass`. Backend unchanged.

### What was built
- **Architecture** exactly as specified (feature folders with `components/ pages/ xSlice xSaga xService xTypes`, `services/api`, `components/{common,layout,feedback}`, `styles/*.scss`), documented in `docs/FRONTEND.md` with a data-flow diagram and a description of each folder.
- **Store:** `configureStore` + saga middleware, `rootReducer`, `rootSaga`, typed hooks. Slices: auth, cart, checkout, home, orders, products, ui (toasts). Every request is a saga calling a service that uses the shared Axios client (base URL from env, 15 s timeout, CSRF header, a 401 interceptor, normalised `SerializedApiError`). No component imports Axios; Stripe's `confirmPayment` is the one SDK call in a component and is commented as such.
- **Request cache** (replaces RTK Query): `utils/keyed.ts` + `keyedSaga.ts` keep per-key `{status, data, error, fetchedAt}` entries with a 60 s TTL, de-duplicate concurrent requests per store and keep stale data on refresh/failure. Back to a view just seen costs no request.
- **UI** rebuilt without MUI: Button, Input, Select, Checkbox, Chip, Alert, Loader/Skeleton, Modal (focus trap, Escape, focus return; also the filter drawer), Menu, Pagination, PriceDisplay, SearchInput (debounced), dual-thumb price slider (two native range inputs), ARIA combobox for the header search, ErrorMessage, EmptyState, Toasts; layout: MainLayout (skip link), Header, Navigation, Footer, Sidebar. SCSS modules with tokens from `styles/variables.scss`.
- **Features:** home block renderer, products (listing with URL state, details with accessible sortable offers table, search with did-you-mean), cart, checkout (+ `PaymentMethod` with the Payment Element), **new `/payment/success` and `/payment/cancel` pages** (the success page never trusts the redirect: it polls the order and moves on to the order page once paid), orders (history and detail with polling saga and key reveal/copy), auth (React Hook Form + zod forms, protected route). Routes changed to the requested ones (`/orders`, `/orders/:id`, `/payment/*`).
- Welcome and receipt e-mails now run from sagas (receipt only after the server says paid, flag consumed once, no keys).

### Mistakes and fixes along the way
- The shared in-flight set of the keyed saga lived at module level, so a never-finishing request in one test's store silently suppressed the same request in the next store (17 tests failed in a block). It is now per saga instance, and a test pins it.
- A flaky checkout test grabbed a Loader element that was replaced a moment later; it now waits on the condition instead of holding the element.
- The store page overflowed by 13 px at 375 px (the sort field kept a 200 px minimum); fixed in the layout, caught by the browser script.
- The account-menu button's initial was real text, which axe flagged as label-in-name; it is now drawn from a data attribute.
- The shell script counted the native sort `<option>`s as search suggestions; it now scopes to the suggestions listbox.

### Limits and open points
- The real card payment still cannot run in the sandbox (no Stripe account or network): Stripe is stood in for in tests and the browser script plays its part with a signed webhook.
- `assets/` and `services/storage/tokenStorage.ts` from the sample tree are not used: there are no static assets beyond the generated SVG art from the API, and no token exists in JavaScript (HttpOnly cookie), so `safeStorage.ts` replaces the idea.
- `FeaturedProducts`/`BestSellerSection`/`DealsSection` are not separate components: all three are the same block type (`carousel`) driven by the database, rendered by one `ProductRail`, which is what makes "reorder or disable a block in the database" work without frontend changes.
- Not done: per-route document titles and focus/announcement on navigation (docs/REVIEW.md O5); the Google font is still a render-blocking third-party stylesheet.

## Response summary

**Found.** One EmailJS module existed (`services/email/emailjs.ts`: a welcome template and a receipt template, browser-sent). There was **no** verification flow at all (no token, endpoint or page), so the "backend generates and validates tokens" requirement meant building it.

**Key decision (security).** A verification link is a secret. If the browser built or received it, anyone could register with another person's address and verify it themselves. So the **API** creates the token (256 random bits, only its SHA-256 stored, 24 h expiry, single use, new link replaces old) and sends the message through EmailJS's REST API with a server-only private key, using the **same AUTH template** as the welcome e-mail. The browser's `sendVerificationEmail()` only asks the API to send a fresh link. Welcome and order e-mails carry no secret and stay browser-sent with the public key. This departs slightly from the literal "frontend sendVerificationEmail(data) via EmailJS"; the reason is written in docs/EMAIL.md.

**Backend.** Migration 007 (`users.email_verified_at`, `email_verifications`), `src/Mail/*` (interface, EmailJS REST mailer, null mailer), `EmailVerificationService`, `POST /api/auth/verify-email` (public, token is the proof), `POST /api/auth/resend-verification` (signed in, 5/hour per account), `emailVerified` added to the user JSON (additive, existing fields unchanged), `https://` required for `APP_URL` outside local, settings/env/compose. Two verified demo accounts are created by the seeder (idempotent, never overwrite): `demo.buyer@keymart.test` / `Demo-Buyer-2027`, `demo.shopper@keymart.test` / `Demo-Shopper-2027`.

**Frontend.** `services/email/{emailConfig,emailTypes,emailHelpers,emailService}.ts` with typed template params, validation of required values and URLs, HTML escaping, results `sent | skipped | invalid | failed` (nothing throws, logs carry no address/payload). Env renamed `VITE_EMAILJS_WELCOME_TEMPLATE_ID` to `VITE_EMAILJS_AUTH_TEMPLATE_ID` (the user must rename it in their own `frontend/.env`). New `/verify-email` page, a "verify your email / send a new link" banner, auth slice/saga additions. Order confirmation refuses any order the server has not marked paid.

**Templates.** `docs/email-templates/auth.html` (registration + verification, optional expiry box via `{{#expiry_message}}`) and `order.html` (facts table, `{{{order_items}}}` rows, subtotal/discount/total, digital-delivery note). Table layout, inline CSS, 600 px, mobile media query, Outlook ghost table, preheader, fallback link, no images, no JS. Previews and example payloads in `docs/email-templates/{previews,examples}`; `scripts/render_email_templates.cjs` renders them (no horizontal overflow at 375 px).

**Verified.** PHPUnit 357 tests (10 new for verification; mutation check: removing the expiry condition fails 2 tests), Vitest 348 (new service, escaping, verify page and banner tests), lint, prettier, tsc, build, Playwright purchase test, previews viewed. Not verified: delivery in real Gmail/Outlook/Apple Mail and EmailJS's handling of `{{#...}}` / `{{{...}}}` (no EmailJS account here); the checklist is in docs/EMAIL.md.

**Trade-offs / open.** Verification is not enforced (a banner only; blocking checkout would be one check). The order e-mail HTML rows are built in the browser (escaped), not by the backend; moving order confirmation into the webhook handler is the stronger design and is recorded as a follow-up. EmailJS offers no separate plain-text part, so the plain-text requirement is met only as far as possible (preheader, fallback links). The REST mailer itself has no automated test. Outlook (Windows) shows square buttons.

**CI.** Run 2 of the P18 workflow finished green on all three jobs (backend, frontend, Playwright e2e), so P18's "CI is green" is met.

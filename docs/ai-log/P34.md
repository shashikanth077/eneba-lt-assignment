## Response summary

**Logging (backend).** New `App\Support\Log`: one JSON line per event on the error stream (what Vercel and Railway collect), levels debug/info/warn/error/off (`LOG_LEVEL`, default info), event names `area.what`, a `request_id` on every line of a request (also returned as `X-Request-Id`; the caller's id is accepted if safe; `x-vercel-id` and `x-railway-request-id` are copied in), `user_id` after sign-in. Secrets are redacted by field name (password, token, cookie, signature, key, secret, card, ...), e-mail addresses are masked, values are cut at 300 characters, and a log call can never fail a request. New `RequestLogMiddleware` (outermost) writes one line per request (5xx error, 4xx warn). Instrumented flows: app start (unsafe config), db errors, unhandled exceptions, health (stock empty), auth (register, login ok/failed with reason, session rejected, verify, resend, profile, password), mail (sent / skipped with the list of missing `EMAILJS_*` settings / failed with HTTP status and EmailJS's own answer), cart (stock), checkout (started, reserved, intent, refused, intent failed, Stripe key missing), webhook (received, rejected with reason, handled with outcome), payment (paid, sync from Stripe, unknown order, refund needed/refunded/refund failed, cancel failed), order expiry, key seeding and secret mismatch, CSRF refusals, rate limits.

**Logging (browser).** Vercel cannot see the browser, where the welcome and order e-mails are sent. New `POST /api/client-log` accepts only a fixed list of events (`email.sent|skipped|invalid|failed`, `payment.poll.gave_up`, `checkout.failed`, `app.error`), chooses the level itself, keeps a few short whitelisted fields, is rate-limited, and the frontend `reportEvent` (never throws, never retries) sends: the result of every e-mail attempt with EmailJS's own error text and the unset `VITE_EMAILJS_*` names, "order paid but no receipt flag in this browser", the payment page giving up, checkout failures, uncaught errors (max 5 per page load).

**Docs.** docs/LOGGING.md: line format, how to read it on Vercel/Railway, the event catalogue, "e-mail did not arrive" and "payment stuck" search recipes, safety.

**README rewritten**: overview with stack table, screenshots (`docs/screens/final/`, generated by `frontend/e2e/readme.screens.cjs`), architecture diagram and purchase sequence diagram (Mermaid), scope table with justifications (in / partial / out, updated to what exists now), data model (table groups plus an ER diagram generated from the live schema), run/config/keys/deployment, logging and troubleshooting, tests and CI, API reference, known limitations, documentation map, layout.

**Also fixed.** The narrow cart panel crammed the item row (name and seller wrapped letter by letter): `CartItem` has a `compact` layout used in the panel. The browse e2e test failed about half the runs under parallel load because it clicked the cover image's centre, where the invisible hover buttons sit; it now clicks the cover link's corner (6/6 passing, 3 full runs).

**Verified.** PHPUnit 411 (new `LogTest`, `FlowLoggingTest`: format, redaction, levels, request ids, masked addresses, every flow's events in order, browser report whitelist, DB-down error line), Vitest 379, lint, build, Playwright 6 flows x3. Real log lines were read from the running API (`http.request`, `auth.login.failed`, `checkout.*`). **Not verified:** the lines on Vercel/Railway themselves (no access): the format is plain stderr JSON, which both platforms collect, but how each UI filters it is the platforms' behaviour. The README's Mermaid diagrams were written carefully but not rendered here; GitHub renders them.

# P27: Guest cart, inventory audit, key management, account page, demo history

## Prompt

Task: Review and Implement Ecommerce Improvements
Carefully inspect the existing project architecture, database schema, APIs, frontend flows, and Git branches before making changes.
Implement the following requirements while preserving the existing architecture and avoiding unnecessary refactoring.
1. Guest Cart and Checkout Authentication

* Allow visitors to add, update, and remove products from the cart without logging in.
* Persist guest cart items across page refreshes.
* When a guest proceeds to checkout, redirect them to sign in or register.
* After successful authentication, preserve and merge the guest cart with the user's cart.
* Require authentication for checkout completion and order history.

2. Inventory and Stock Management

* Audit and correct the complete product availability and inventory logic.
* Ensure stock quantities, out-of-stock status, product listings, product details, cart, and checkout remain consistent.
* Prevent purchasing quantities greater than available stock.
* Validate inventory on the backend during checkout.
* Handle concurrent purchases safely to prevent overselling.
* Ensure stock updates correctly after successful orders and cancellations.

3. Product Images and Seed Data

* Generate suitable, unique product images for demo products where images are currently missing.
* Update existing seed data to associate products with appropriate images.
* Use consistent image dimensions and quality.
* Avoid unrelated, duplicate, or misleading product images.
* Preserve existing product information and database relationships.

4. Demo Accounts and User Profile

* Provide predefined demo login accounts for testing before registration.
* Include the required account functionality:
   * Edit Profile
   * My Orders
   * Change Password
* Ensure demo accounts have realistic test data and appropriate permissions.
* Never expose production credentials or sensitive user information.

5. Git Branch and Code Push

* Fetch the latest changes from `master`.
* Review the existing branch status and uncommitted changes before proceeding.
* Create a new feature branch from the latest `master`.
* Implement and test the changes on the new branch.
* Commit and push the completed changes to the remote repository.
* Do not overwrite or discard existing work.

6. Game Key Management

* Investigate why game keys are being regenerated or reseeded repeatedly.
* Design a reliable approach for managing game keys as inventory records.
* Ensure each key is generated or imported only when required.
* Store keys securely using the existing encryption mechanism.
* Track key availability, assignment, reservation, and delivery.
* Prevent duplicate assignment or reuse of delivered keys.
* Ensure keys are not lost or regenerated during application restarts, deployments, or repeated seed execution.
* Preserve existing encrypted keys and provide a safe migration strategy if necessary.

Implementation Requirements

* Inspect existing code and database structures before implementation.
* Reuse existing APIs, services, components, and database relationships wherever possible.
* Do not invent endpoints, tables, columns, or configuration variables.
* Do not use dummy API endpoints or hardcoded production data.
* Make database seeders safe to execute repeatedly (idempotent).
* Test all affected frontend and backend flows.
* Report implemented changes, database changes, test results, and Git branch/commit/push details.
* Clearly identify any blockers instead of claiming incomplete work is finished.

## Response summary

Branch `claude/ecommerce-improvements` created from the fetched `origin/master` (master already contained every earlier branch of this project plus the owner's own commits, so nothing was lost; the working tree was clean).

**Guest cart.** Kept in the browser (localStorage), merged by the existing `POST /api/cart` after sign-in or registration (no new endpoint, the server re-checks stock and limits); `/cart` is public, checkout and orders stay protected, "Sign in to check out" / "Create an account" keep `?next=/checkout`. Prices/stock of guest lines are re-read from the public product endpoint when the cart page opens.

**Inventory audit.** Stock is one definition (keys in `available`) used by lists, filters, product page, cart and checkout; cart and checkout validate quantity against it on the server; checkout reserves with `FOR UPDATE SKIP LOCKED` in one transaction; failure/cancel/expiry release keys; existing concurrency tests pass. Gap found and fixed: keys behind an expired reservation stayed unavailable until somebody closed that order, now also released by `GET /api/health`. Gaps NOT changed: none known.

**Keys.** Investigation, design, migration 008 (`sold_at`), random keys created once per offer, decrypt-guard, `bin/import_keys.php`, docs/KEYS.md.

**Account.** `PATCH /api/auth/profile`, `POST /api/auth/change-password` (current password required, other sessions revoked, rate-limited), `/account` page, menu link. Demo accounts: two, with realistic paid orders created once; password change blocked for them (403) so the shared accounts cannot be locked; stated openly because it limits what a reviewer can try with them.

**Images.** Audited, no change: all 120 products already have a unique generated SVG cover (same 400x533 size, from the title, no third-party art); real game artwork cannot be generated or licensed here. Not claimed as improved.

**Fixed along the way (owner's master commit "api bug fixes / add to cart"):** 14 frontend and 4 backend tests had been left red by the new card actions and `offerId`, and `offerId` on the product-detail response produced an undefined-index warning; tests updated, `?? null`.

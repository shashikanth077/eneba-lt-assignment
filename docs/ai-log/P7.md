## Response summary

- **Interpretation of the last line**: it answers my two open questions from P6: (1) out-of-stock products must be searchable and shown as out of stock; (2) `q` with relevance sorting must exist on the catalog endpoint (`GET /api/products`). Both implemented.
- **Implemented**: `GET /api/search` (same engine as `/api/products?q=`, `q` required, results carry `score`), `GET /api/search/suggest` (best 6, empty below 2 chars, out-of-stock included and flagged), and `q` + `sort=relevance` on `/api/products` (relevance is the default when `q` is present, 422 without `q`). `/api/filters` accepts `q` too, so the sidebar can count search results.
- **Code**: `TextNormalizer` (diacritic table without the intl extension; the seeder now uses the same function), `Scorer` (pure re-ranking function), `SearchRepository` (one capped LIKE statement ordered by number of pattern hits), `SearchService` (rank, threshold 0.40, suggest), catalog changes (`searchIds` filter, `ProductSort::Relevance` via `FIELD()`, `LEFT JOIN` when searching, price sorts put out-of-stock last), `inStock` added to every card (and `fromPriceCents` may be null).
- **Scoring**: per-word Levenshtein (word order irrelevant), partial-word and in-word credit, pg_trgm-style trigrams (containment + Jaccard), exact/prefix bonuses, a coverage penalty so "wither 3" does not return every title ending in "3". Tuned in two steps after looking at real scores (a shared digit alone scored 0.45; "punk" had no credit inside "cyberpunk"; the "unmatched word" threshold 0.5 let "wither"~"the" through, raised to 0.6).
- **Documented** in `docs/SEARCH.md` (formulas, complexity O(P x K) SQL scan + O(C x Tq x Tt x L^2) bounded re-rank, measurements, scale limit, production choice) and `docs/ARCHITECTURE.md` (section 7 rewritten as built, API table and types updated).
- **Measured** (MariaDB sandbox): SQL candidate pass 0.6 ms @120 products, 16 ms @10k, 76 ms @50k, 144 ms @100k (two-typo query ~1.5x); PHP re-rank flat ~1 ms thanks to the 200 cap. My stated limit: comfortable to ~10-20k, acceptable to ~50k, then use Meilisearch/Typesense (or OpenSearch at larger scale; pg_trgm if we were on PostgreSQL).
- **Tests**: 158 pass (was 74). `SearchTest` has a **29-case** query table (typos, partial, word order, diacritics, hyphen/apostrophe, injection string, `%`/`_`, nonsense, out-of-stock), plus score ordering, out-of-stock behaviour, `q` on `/api/products` with filters/sorts/pagination/facets, 422 cases, suggest (top 6, short queries), candidate cap. `SearchScoringTest` (unit) and `SearchSeededTest` (all 120 seeded titles searched mangled: exact, upper-case+punctuation, reversed, one letter dropped, two swapped must find themselves; partial names keep the title in the results; a word's results equal a SQL ground truth). Mutation check: no noise filter, no typo tolerance, out-of-stock hidden, cap ignored, coverage penalty off were each caught (my first "mutation 5" was a no-op because its sed pattern matched nothing; redone properly).
- **Bugs found on the way (mine)**: `Validator` accepted a whitespace-only value for `required` (presence was checked before trimming), fixed with a regression test (hardens every endpoint); my fixture accidentally had two "silksong" titles; a trigram-set test compared unsorted key lists; a "first 5 letters" test expected a unique title where several legitimately share the prefix (replaced by a recall test); an awkward placeholder in a data provider.
- **Known limits (documented)**: filters apply after the top-200 cut; no synonyms/abbreviations (`gta`), no stemming; weights hand-tuned; `/search/suggest` has no rate limit yet (ARCHITECTURE lists 429 for it); sold-out ordering inside relevance is by score only (no in-stock preference on ties).
- **Not verified**: MySQL 8 (everything ran on MariaDB 10.11); `docker compose up` (no daemon). Frontend not touched.

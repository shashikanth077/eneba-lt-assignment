# P35: EmailJS recipient-address fix

## Prompt

Please investigate and fix the EmailJS recipient-address issue across all email workflows: registration, email verification, and order confirmation.
1. Registration and Email Verification
* The recipient email address is currently empty, causing an error when sending registration and verification emails.
* Trace the complete flow from the registration form through the backend/frontend integration to the EmailJS send request.
* Identify why the recipient email field is missing, incorrectly mapped, or not populated.
* Ensure the registered user's actual email address is passed correctly to the EmailJS recipient field.
* Verify that the correct template parameters and EmailJS configuration are used.
* Ensure registration and email verification work correctly without hardcoded or dummy email addresses.
2. Order Confirmation Email
* Perform the same investigation for the order confirmation workflow.
* Ensure the recipient email is retrieved from the authenticated customer's actual account/order information.
* Verify that the correct recipient address and order details are passed to the existing EmailJS order confirmation template.
* Ensure the email is triggered only after successful payment confirmation, following the existing payment and webhook flow.
* Prevent duplicate order confirmation emails.
3. Validation and Error Handling
* Validate that the recipient email exists and is not empty before attempting to send an email.
* Add meaningful error handling and logging to identify missing recipient addresses or incorrect template parameters.
* Do not expose sensitive information, API keys, or customer data in logs.
* Handle EmailJS failures gracefully without incorrectly marking registration, verification, or orders as successful.
4. Testing and Verification
Test all three workflows end to end:
* New user registration email.
* Email verification email.
* Successful order confirmation email.
Confirm that:
* The correct recipient email is populated in every EmailJS request.
* Each workflow uses its intended existing email template.

## Response summary

**Finding.** Tracing all three flows, the code already sends the real account address as `to_email` (registration: server-returned user after sign-up; verification: `users.email` in the API; order: the signed-in user, only when the server reports the order `paid`, one-shot receipt flag prevents duplicates). No hardcoded address exists. The most likely cause of EmailJS's "recipients address is empty" is therefore the EmailJS dashboard template, whose *To email* field must be exactly `{{to_email}}`; that cannot be inspected from this environment and is stated honestly in the docs.

**Changes.**
- Frontend `emailService.ts` / `emailHelpers.ts`: recipient also sent as `email` and `user_email` (templates using those names resolve); `looksLikeEmail` check refuses an empty or malformed address before calling EmailJS (`email.invalid`, address never logged).
- Backend `EmailJsVerificationMailer.php`: same aliases; refuses an invalid recipient (`mail.verification.invalid_recipient`); injectable transport so the REST payload is testable. `EmailVerificationService::sendTo` validates the address before creating a token.
- Tests: new `EmailJsMailerTest` (payload recipient, AUTH template id, empty/malformed refused, provider refusal = not sent); Vitest for aliases on both templates and malformed-address refusal. Existing tests cover order e-mail only after `paid` and no duplicates.
- Docs: `docs/EMAIL.md` troubleshooting section, `docs/LOGGING.md` event table.

**Verification.** PHPUnit 414 passed, Vitest passing, tsc/eslint/prettier clean. A real EmailJS delivery could not be tested here (no keys, no network to EmailJS).
